Part 03

Building the platform

A CLI, a pipeline and three layers of modeling.

Provisioning CLI go · terraform · terragrunt

The provisioning CLI

One Go image: binary, ClickHouse client, Terraform and a SQL linter.

  • Noun-verb: actions live next to the resource they touch
  • SQL is the source of truth: numbered, immutable migrations
  • Fixes never edit a migration; a new numbered file, diff in the MR
Guardrails test before apply

Safety built into the workflow

Catch the problem in seconds, on your machine, not in production.

  1. 01

    Local tests first

    Testcontainers spins up disposable ClickHouse plus a local AWS emulator; data must reach the final table.

  2. 02

    Plan gates

    apply aborts when the Terraform plan would replace or destroy a production pipeline.

  3. 03

    Automatic rollback

    A failed pipeline phase undoes the run; table and pipeline stay consistent.

  4. 04

    AI-assisted schema

    Schema inferred from sanitized samples, ClickHouse best practices, human review mandatory.

  5. 05

    One rule, many tenants

    Parameterized templates rendered per warehouse, with a guard that fails on drift.

Ingestion figure 2 · s3 → clickpipes → clickhouse

End-to-end ingestion

Kubernetes audit, CloudTrail, identity providers, EDR, SWG, DNS, application audit: all into S3, all into ClickHouse.

01Collection: logs land in S3 (4d)
02Notification: SQS gets ObjectCreated
03Ingestion: ClickPipes → source tables
04Normalization: materialized views
05Queryable: final tables, long-term retention

Freshness of seconds to minutes. Need sub-10 seconds? ClickPipes supports Kafka natively.

Why managed over the native engine: push via SQS, no bucket listing, tracking handled for you, no per-GB cost.

Part 04

Detection & hunting

From versioned SQL to a Slack ping, and an agent on the hunt.

Detection sql → slack

Detections are code

A detection starts as a versioned SQL file and ends as a Slack notification.

  • An alert fires when the query returns rows: the WHERE clause is the condition
  • Each finding carries a class matched to its detection manifest
  • The match routes it to the right channel and the right owner
  • Failed runs notify too: exponential backoff, root cause preserved
  • Now capable of running alerts every 10 minutes or less; the old platform capped at 1×/hour
  • 99% of the alerts run in up to 15 seconds
Access zero direct access

Access and identity

No user accesses ClickHouse directly.

  • All human access is mediated by the notebook platform*
  • SSO via OIDC, authorized by the corporate identity manager
  • ACLs inherited through the folder hierarchy
What ClickHouse sees
  • One ClickHouse user per real user: a strict 1-to-1 mapping
  • Credentials stored encrypted in the database; analysts never touch them
  • Every query auditable: platform logs and system.query_log

* notebook platform — github.com/The-Heaven-Labs/aether-notebooks

Threat hunting agentic · aggregate-first

Agentic threat hunting, aggregate-first

10–15 hypotheses run in parallel. Techniques map to MITRE ATT&CK; every run is traceable in Langfuse.

  1. 01

    Mandatory aggregation

    Baseline over the whole campaign window: event volume per user, per day.

  2. 02

    LLM-guided drill-down

    The agent picks the next query, evaluates findings, decides what to look at next — and why.

  3. 03

    Domain rules

    Proxy blocks, remote access tools, data staging: calibrate each step's confidence.

  4. 04

    Verdict per hypothesis

    Verdict, confidence, indicators and suggested detections in its own result cell.

Observability three fronts

Platform health, three fronts

Infrastructure metrics can't see everything, including real freshness.

  • Ingestion: ClickPipes metrics in Datadog
  • Batch execution: worker metrics in Prometheus
  • Real freshness: in-house monitor measuring source delay inside ClickHouse
Lesson · stale metrics
  • A stopped ClickPipe's series can vanish from Prometheus: no zero, no "stopped" label
  • Datadog may keep showing the last aggregated value
  • Rule: confirm any suspicion on the source-of-truth endpoint

What the build bought us

Six reasons the trade-off paid off.

  1. 01

    Own the choices

    Not everything is self-hosted, but every piece is a deliberate, revocable choice.

  2. 02

    Flexibility without ceilings

    Support whatever we want, however we want; no vendor roadmap required.

  3. 03

    Performance as leverage

    People and agents do more in less time when queries answer in seconds.

  4. 04

    Retention that pays off

    A two-year-old incident stays queryable: no log rehydration, no archive archaeology.

  5. 05

    Radically lower TCO

    Estimated at 10% or less of a comparable Elastic SIEM at our scale.

    Invest in people

    Budget goes to what your team builds, not to products you rent.
